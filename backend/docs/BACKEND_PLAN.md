# ArchNG Backend Plan

Draft of 2026-11-16. Express, PostgreSQL and Prisma, written in JavaScript (ES modules).

## 1. Overview

This plan fixes how the ArchNG API is built, so every endpoint has the same layers, the same response envelope and the same error handling. It covers the MVP in `AGENTS.md` (phases 1 to 5): auth, providers, projects, uploads, demo requests, favorites and admin. The data model is the Prisma draft in `AGENTS.md` section 6.

Foundations:

| Area | Choice |
| --- | --- |
| Runtime and framework | Node.js with Express, plain JavaScript as ES modules (`"type": "module"`, imports end in `.js`) |
| Database | PostgreSQL with Prisma (eight models at MVP: User, ProviderProfile, Experience, Project, ProjectImage, Specialty, DemoRequest, Favorite; Review later) |
| Roles | `USER`, `PROVIDER`, `ADMIN` (Prisma enum) |
| IDs | UUID strings |
| Validation | Zod. Request-body schemas live in `packages/shared`; the API's `validators/` folder composes them and adds param and query schemas |
| Types | None required. Use JSDoc on shared helpers where it helps editors, and optionally `// @ts-check` |
| Tests | Vitest and Supertest |

The golden rules: controllers stay thin, services hold the logic, every async handler is wrapped, and **gated fields never leave the API through a public response** (see contract C12).

## 2. Architecture and layers

Every request travels the same path, and each layer owns one kind of work.

```text
Client            React app sends a request with a JWT to /api/v1
   |
   v
Route             maps the URL and sets the middleware chain
   |
   v
Middleware        authenticate, requireRole, validate, rate limit
   |
   v
Controller        reads req, calls one service, sends the envelope
   |
   v
Service           gating, ownership, transitions, emails, transactions
   |
   v
Prisma client     typed queries, schema, migrations
   |
   v
PostgreSQL        tables, indexes, unique and foreign keys
```

**Layer responsibilities**

| Layer | Owns | Does not own |
| --- | --- | --- |
| Routes | URL mapping and the middleware chain for each endpoint | Business logic |
| Middleware | Cross-cutting checks: authentication, role checks, validation, rate limiting, error formatting | Domain rules |
| Controllers | Translating HTTP to a service call and the result to the response envelope | Database queries and business rules |
| Services | Business logic and orchestration: gating, ownership, status transitions, emails, transactions | HTTP concerns (`req`, `res`, status codes) |
| Prisma (model layer) | Data shape, relations, unique constraints, indexes, migrations | Business logic |

Only services import the Prisma client. A controller never touches the database, and a service never touches `req` or `res`.

**Golden rule.** Controllers stay thin and services hold the logic. A controller should be roughly this:

```js
export const createDemoRequest = asyncHandler(async (req, res) => {
  const request = await demoRequestService.createRequest(req.user.id, req.body);
  created(res, request, 'Demo request sent');
});
```

All the "does this provider exist and is it published? is there already an active request? is this transition allowed?" checking happens in the service.

## 3. Directory layout

The API lives in `apps/api`. Phase 0 creates and then freezes the foundation (config, constants, middleware, utils, app, server, schema). Feature work only adds files to the folders marked with an arrow.

```text
apps/api/
├── prisma/
│   ├── schema.prisma     data model (change only through a reviewed migration)
│   ├── migrations/       generated by prisma migrate
│   └── seed.js           sample architects, projects, specialties (labelled sample)
├── src/
│   ├── config/           env (Zod-validated), db (Prisma client singleton), swagger, storage, mailer
│   ├── constants/        roles, demoRequestStatus, verificationStatus, errorCodes, httpStatus, budgetRanges
│   ├── controllers/      ← you create files here (one per module)
│   ├── middleware/       authenticate, requireRole, validate, rateLimit, notFound, errorHandler
│   ├── routes/           index.js (mounts /api/v1) plus one router per module (fill in your own)
│   ├── services/         ← you create files here (all business logic)
│   ├── serializers/      ← you create files here (public and private response shapes)
│   ├── validators/       ← you create files here (params, query, and compositions of shared schemas)
│   ├── utils/            ApiError, apiResponse, asyncHandler, jwt, password, slugify, pagination
│   ├── app.js            Express assembly (frozen after phase 0)
│   └── server.js         entry point (frozen after phase 0)
└── tests/                ← you create test files here
    ├── unit/             services, utils, the demo request state machine
    ├── integration/      supertest against a test database
    └── helpers/          factories, auth helpers, test database reset

packages/shared/          Zod body schemas and enums used by both the API and the React app
```

**File naming.** One file per module and layer, named `<module>.<layer>.js`, for example `demoRequest.service.js`, `demoRequest.controller.js`, `demoRequest.routes.js`, `demoRequest.validator.js`, `demoRequest.serializer.js`.

**Ownership of changes.** `app.js` and `server.js` are not edited for features; a new feature router is mounted by one line in `routes/index.js`. `schema.prisma` changes need a migration and an update to `AGENTS.md`.

**Constants instead of enums.** Without TypeScript enums, constants are frozen objects, for example:

```js
export const ROLES = Object.freeze({ USER: 'USER', PROVIDER: 'PROVIDER', ADMIN: 'ADMIN' });
```

## 4. Shared contracts

These are built in phase 0 and exist before any feature work. Use them and never re-invent them. They are numbered C1 to C13 so other sections can refer to them.

### C1. Response envelope

`src/utils/apiResponse.js`: every success response uses one of these helpers.

| Helper | Status | Shape |
| --- | --- | --- |
| `success(res, data, msg)` | 200 | `{ success, message, data }` |
| `created(res, data, msg)` | 201 | Same shape as success |
| `noContent(res)` | 204 | Empty body |
| `paginated(res, items, meta)` | 200 | `{ success, data[], pagination }` |

```js
import { success, created, noContent, paginated } from '../utils/apiResponse.js';
success(res, provider, 'Provider retrieved successfully');
paginated(res, providers, { page: 1, limit: 20, total: 100 });
// pagination: { page, limit, total, totalPages }
```

Controllers do not call a failure helper. They throw an `ApiError` and the error middleware formats it as the failure envelope:

```json
{
  "success": false,
  "message": "Validation failed",
  "code": "VALIDATION_FAILED",
  "details": [{ "path": "body.budgetRange", "message": "Required" }]
}
```

### C2. Errors

`src/utils/ApiError.js`, with codes in `src/constants/errorCodes.js`.

```js
import { ApiError } from '../utils/ApiError.js';
import { ERROR_CODES } from '../constants/errorCodes.js';

throw ApiError.badRequest('Invalid input');                                         // 400
throw ApiError.unauthorized('Login required', ERROR_CODES.TOKEN_INVALID);          // 401
throw ApiError.forbidden('Provider access required');                              // 403
throw ApiError.notFound('Provider not found', ERROR_CODES.PROVIDER_NOT_FOUND);     // 404
throw ApiError.conflict('Email already in use', ERROR_CODES.EMAIL_ALREADY_EXISTS); // 409
throw ApiError.validation('Validation failed', details);                           // 422
throw ApiError.tooManyRequests('Too many requests', ERROR_CODES.RATE_LIMITED);     // 429
throw ApiError.internal('Something went wrong');                                   // 500
```

Rule: error codes are imported from `ERROR_CODES`, never typed inline.

| Group | Codes |
| --- | --- |
| Auth | EMAIL_ALREADY_EXISTS, INVALID_CREDENTIALS, ACCOUNT_SUSPENDED, TOKEN_INVALID, TOKEN_EXPIRED |
| Providers | PROVIDER_NOT_FOUND, PROVIDER_SLUG_TAKEN, PROVIDER_NOT_PUBLISHED, VERIFICATION_ALREADY_PENDING, VERIFICATION_NOT_PENDING |
| Projects | PROJECT_NOT_FOUND |
| Demo requests | DEMO_REQUEST_NOT_FOUND, DUPLICATE_ACTIVE_REQUEST, INVALID_DEMO_REQUEST_TRANSITION, REQUEST_NOT_CANCELLABLE, DEMO_ACCESS_NOT_GRANTED |
| Media | INVALID_VIDEO_URL, UPLOAD_TYPE_NOT_ALLOWED |
| Taxonomy and favorites | SPECIALTY_NOT_FOUND, FAVORITE_ALREADY_EXISTS, FAVORITE_NOT_FOUND, FAVORITE_TARGET_NOT_FOUND |
| Generic | VALIDATION_FAILED, RATE_LIMITED, INTERNAL_ERROR |

### C3. Async handlers

`src/utils/asyncHandler.js`: every async route handler is wrapped, so a rejected promise reaches the error middleware instead of crashing the process. Express 5 handles rejections natively, but the wrapper stays for uniformity and Express 4 compatibility.

```js
router.get('/', asyncHandler(async (req, res) => {
  // throws here are caught by the error middleware automatically
}));
```

### C4. Validation

`src/middleware/validate.middleware.js` uses Zod. Pass a schemas object with any of `body`, `params`, `query`. On success the parsed values replace `req.body`, `req.params` and `req.query`; on failure it returns a 422 with details for every failing field. Request-body schemas come from `packages/shared`, so the React forms and the API validate identically.

```js
// packages/shared/src/demoRequest.js
import { z } from 'zod';
import { BudgetRange } from './enums.js';

export const createDemoRequestSchema = z.object({
  providerId: z.string().uuid(),
  projectType: z.string().min(1).max(80),
  location: z.string().min(1).max(120),
  budgetRange: z.nativeEnum(BudgetRange),
  message: z.string().min(10).max(500),
});

// apps/api/src/routes/demoRequest.routes.js
router.post('/', authenticate, requireRole(ROLES.USER), requestLimiter,
  validate({ body: createDemoRequestSchema }), createDemoRequest);
```

IDs are UUIDs (`z.string().uuid()`). Query numbers use `z.coerce.number()`.

### C5. Auth middleware

```js
router.get('/me', authenticate, handler);                                    // any signed-in account
router.post('/', authenticate, requireRole(ROLES.PROVIDER), handler);        // providers only
router.patch('/:id/status', authenticate, requireRole(ROLES.ADMIN), handler); // admins only
```

After `authenticate` succeeds, `req.user` is `{ id, role }`, where `id` is the user's UUID and `role` is `'USER'`, `'PROVIDER'` or `'ADMIN'`. `authenticate` verifies the token, loads the account, and rejects suspended accounts with `ACCOUNT_SUSPENDED` (403). `requireAdmin`, `requireProvider` and `requireUser` are shorthand for `requireRole`.

Ownership is enforced in services, not middleware: queries are scoped by owner (for example `where: { id, providerId: profile.id }`), so another provider's project comes back as a 404 rather than revealing that it exists.

### C6. JWT helpers

`src/utils/jwt.js`

```js
import { signAccessToken, verifyAccessToken } from '../utils/jwt.js';
const accessToken = signAccessToken({ sub: user.id, role: user.role });
```

The access token is short-lived (`JWT_EXPIRES_IN`). `authenticate` re-reads the account on every request, so role changes and suspensions take effect immediately, at the cost of one primary-key lookup per request. `signRefreshToken` and `verifyRefreshToken` exist but stay unused until the refresh-token decision is made.

### C7. Slugify

`src/utils/slugify.js`

```js
slugify('Adaeze Okafor Studio'); // 'adaeze-okafor-studio'
```

The provider slug is created with the profile and must be unique. The service appends `-2`, `-3` and so on on a collision, and retries if Postgres reports a unique violation. The slug stays stable after creation, so public URLs do not break when a name changes.

### C8. Rate limiting

The global limiter is already applied to `/api` in `app.js`. Sensitive routes add a stricter limiter:

| Limiter | Applied to |
| --- | --- |
| `authLimiter` | `POST /auth/register`, `POST /auth/login` |
| `requestLimiter` | `POST /demo-requests` |
| `uploadLimiter` | `POST /uploads/sign` |

```js
router.post('/login', authLimiter, validate({ body: loginSchema }), login);
```

A blocked request returns a 429 with `RATE_LIMITED` through the normal error path.

### C9. Prisma client and models

All eight models are in `schema.prisma`. Import the single client from `config/db` and never create another one:

```js
import { prisma } from '../config/db.js';

const profile = await prisma.providerProfile.findUnique({ where: { slug } });
```

Schema field names are frozen. If a field looks missing or wrong, raise it before changing anything; the change then goes in as a migration.

### C10. Demo request transitions

`src/constants/demoRequestStatus.js` is the only place that defines the state machine.

| From | To | Actor | Side effects |
| --- | --- | --- | --- |
| REQUESTED | ACCEPTED | Provider | Set `videoAccessGrantedAt`, email the user |
| REQUESTED | DECLINED | Provider | Save the optional note, email the user |
| REQUESTED | CANCELLED | User | None |
| ACCEPTED | COMPLETED | Provider | None |

```js
if (!canTransition(request.status, DEMO_REQUEST_STATUS.ACCEPTED, ROLES.PROVIDER)) {
  throw ApiError.conflict('Invalid status transition',
    ERROR_CODES.INVALID_DEMO_REQUEST_TRANSITION);
}
if (!isCancellable(request.status)) {
  throw ApiError.conflict('Request can no longer be cancelled',
    ERROR_CODES.REQUEST_NOT_CANCELLABLE);
}
```

A user may hold only one active request (REQUESTED or ACCEPTED) per provider and project type; a second one fails with `DUPLICATE_ACTIVE_REQUEST`.

### C11. Pagination

`src/utils/pagination.js` turns the query string into `{ page, limit, skip, take }` (defaults page 1 and limit 20, maximum limit 50). Count and rows come from one transaction.

```js
const { page, limit, skip, take } = parsePagination(req.query);
const [items, total] = await prisma.$transaction([
  prisma.providerProfile.findMany({ where, skip, take, orderBy }),
  prisma.providerProfile.count({ where }),
]);
return { items, meta: { page, limit, total } };
```

### C12. Gated fields: serializers and the access check

This is ArchNG's most important rule: **contact details and the demo video link never appear in a public response.**

| Field group | Who may receive it |
| --- | --- |
| `contactEmail`, `contactPhone`, `whatsapp`, `website`, `demoVideoUrl`, `demoVideoSource` | The owning provider, an admin, and a user with an ACCEPTED request to that provider |
| `registrationNumber`, `verificationDocUrl`, `verificationNote` | The owning provider and admins only |
| `passwordHash` | Nobody |

- Responses are built by serializers in `src/serializers/` (`toPublicProvider`, `toOwnerProvider`, `toAdminProvider`, `toGatedAccess`), each with an explicit field whitelist. Never spread a Prisma object into a response.
- Public service methods also use Prisma `select` to leave the gated columns out of the query (a second line of defence).
- One helper decides access, and every gated endpoint calls it:

```js
// src/services/access.service.js
/**
 * @param {{ id: string, role: string }} viewer
 * @param {string} providerProfileId
 * @returns {Promise<boolean>}
 */
export async function hasGatedAccess(viewer, providerProfileId) {
  // owner, admin, or a user with an ACCEPTED request to this provider
}
```

It returns true for the owner, for an admin, and for a user with an ACCEPTED request. Whether COMPLETED also grants access is an open decision, so it lives in this one function.

### C13. Email

`src/services/email.service.js` wraps Resend or Nodemailer behind a small interface: `sendDemoRequestCreated`, `sendDemoRequestAccepted`, `sendDemoRequestDeclined`, `sendVerificationResult`. Emails are sent after the database change commits, and a failed send is logged and never fails the request.

## 5. Feature modules

Each module has a route, controller, service, validator and (where it returns provider or request data) a serializer, all named `<module>.<layer>.js`. Endpoint paths and guards match the API table in `AGENTS.md`, mounted under `/api/v1`.

| Module | Endpoints and guards | What the service owns |
| --- | --- | --- |
| auth | `POST /auth/register`, `POST /auth/login` (public, `authLimiter`); `GET /auth/me` (any role) | Unique email, password hashing, creating a USER or a PROVIDER with an empty profile and unique slug, refusing ADMIN self-registration, refusing suspended accounts, issuing the JWT |
| provider (public) | `GET /providers`, `GET /providers/:slug` (public) | Showing only published providers on ACTIVE accounts; keyword, state, city, specialty, experience and verified filters; verified-first ranking; the public serializer with no gated fields |
| providerProfile (me) | `PUT /me/provider-profile`, `POST /me/provider-profile/verification`, `PUT /me/demo-video` (PROVIDER) | Updating profile, experience and specialties; submitting verification (status becomes PENDING, rejected if already pending); validating the demo link as YouTube or Vimeo and deriving its source; publishing rules |
| project | `GET /projects`, `GET /projects/:id` (public); `POST`, `PATCH`, `DELETE /me/projects` (PROVIDER) | Owner-scoped create, edit and delete; image order and cover image; status changes between DRAFT, PUBLISHED and HIDDEN; public lists showing only PUBLISHED projects of published providers |
| upload | `POST /uploads/sign` (PROVIDER, `uploadLimiter`) | Allowed file types and size limits; signed parameters for Cloudinary or S3 under a per-provider folder |
| specialty | `GET /specialties` (public); `POST /admin/specialties` (ADMIN) | Unique names and slugs; lists used by the filters |
| demoRequest | `POST /demo-requests`, `GET /me/demo-requests`, `PATCH /demo-requests/:id/cancel`, `GET /demo-requests/:id/access` (USER); `GET /provider/demo-requests`, `PATCH /demo-requests/:id/accept`, `decline`, `complete` (PROVIDER) | Target provider must be published and active; one active request per user, provider and project type; the state machine (C10); access check and gated response (C12); emails |
| favorite | `POST /favorites`, `DELETE /favorites/:id`, `GET /me/favorites` (USER) | Target must exist and be public; no duplicates; owner-scoped delete |
| admin | `GET /admin/stats`, `GET /admin/providers`, `PATCH /admin/providers/:id/verification`, `PATCH /admin/users/:id/status`, `PATCH /admin/projects/:id/visibility` (ADMIN) | Dashboard counts; the verification queue and VERIFIED or REJECTED decisions with a reason and email; suspending and restoring accounts; hiding and restoring projects |

Supporting pieces with no routes of their own: `access.service` (C12), `email.service` (C13), the storage client in `config/`, and `GET /health` for deployment checks.

## 6. Prisma and Postgres conventions

- **One client.** `config/db.js` exports a single Prisma client, cached on `globalThis` in development so hot reloads do not open extra connections. Only services import it.
- **Migrations.** Use `prisma migrate dev` locally and `prisma migrate deploy` in CI and production. Commit every migration and never edit one that has been applied.
- **Transactions.** Multi-step writes (create a request after checking for a duplicate, accept a request and stamp `videoAccessGrantedAt`, submit verification) run inside `prisma.$transaction`.
- **Duplicate active requests need a database rule, not only a check.** Two simultaneous requests could both pass a service check. Add a partial unique index in a migration through raw SQL, because Prisma's schema language cannot express it:

```sql
CREATE UNIQUE INDEX demo_request_one_active
  ON "DemoRequest" ("userId", "providerId", "projectType")
  WHERE status IN ('REQUESTED', 'ACCEPTED');
```

- **Error mapping.** Services throw domain errors (`ApiError` with an `ERROR_CODES` entry) for every expected case. As a safety net, the error middleware also maps Prisma errors: P2002 (unique violation) to a 409, P2025 (record not found) to a 404, and P2003 (foreign key) to a 409.
- **Search.** At MVP, keyword search uses case-insensitive `contains` over provider headline and bio and project title and description. Keep it behind one `searchProviders` function so it can later move to Postgres full-text search (a `tsvector` column with a GIN index, queried through `$queryRaw`) without touching controllers.
- **Selecting fields.** Public queries use `select` to name the columns they need, which also keeps gated columns out of memory (C12). Avoid loading whole relations when a count or a few fields will do.
- **Deleting.** Deleting a project cascades to its images. Accounts are suspended, not deleted, in the MVP.
- **Seeding.** `prisma/seed.js` is idempotent (upserts) and creates specialties, sample architects and projects labelled as sample content, and the first admin from `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD`. Seeding is the only way to create an ADMIN, since registration refuses that role.
- **Environments.** `DATABASE_URL` points at a managed Postgres in production; tests use a separate `archng_test` database.

## 7. Testing and definition of done

Tools: Vitest as the runner and Supertest for HTTP tests, against the `archng_test` database. Migrations run once before the suite and tables are truncated between tests. Email and storage clients are mocked.

| Kind | Where | What it covers |
| --- | --- | --- |
| Unit | `tests/unit/` | Services, utils, and the demo request state machine (a table-driven test over every from, to and actor combination) |
| Integration | `tests/integration/` | Each route through the real middleware chain and database |
| Helpers | `tests/helpers/` | Factories for users, providers, projects and requests; a function that signs in as a role; database reset |

**Tests that must always exist**

- **Permission matrix.** For every protected endpoint, no token gives 401, the wrong role gives 403, and another owner's resource gives 404.
- **Gated-field contract test.** Every public endpoint's JSON is scanned for the gated keys in C12, and none may appear. The access endpoint is tested for the owner, an admin, a user with an ACCEPTED request, and a user without one.
- **State machine and duplicates.** Invalid transitions return 409, and a second active request to the same provider and project type is refused, including under two simultaneous calls.
- **Envelope and errors.** Success responses match C1, and validation failures return 422 with a details entry per failing field.

**Definition of done for every endpoint**

- [ ] Route with the guard chain in the right order (authenticate, role, rate limiter, validate)
- [ ] Zod schema in `packages/shared` (body) and `validators/` (params and query)
- [ ] Controller is thin, wrapped in `asyncHandler`, and responds with an envelope helper
- [ ] Business rules live in the service; only the service touches Prisma
- [ ] Response goes through a serializer; no gated or private fields leak
- [ ] Errors are `ApiError` with a code from `ERROR_CODES`
- [ ] Unit tests for the service and integration tests for success, auth failure and validation failure
- [ ] OpenAPI (Swagger) annotation added
- [ ] Lint and the whole test suite pass

Phases 0 to 5 make the backend MVP and line up with phases 1 to 5 in `AGENTS.md`. The React app can start against the OpenAPI docs once phase 2 lands.

## 9. Open decisions and AGENTS.md changes

**Open decisions**

- [ ] Format of `packages/shared`: JavaScript with JSDoc (the React app, which is TypeScript, still infers types from the Zod schemas when `allowJs` is on) or a small TypeScript package compiled to JavaScript for the API
- [ ] Refresh tokens, and where the JWT lives on the client (HTTP-only cookie or memory)
- [ ] Whether COMPLETED requests keep contact and video access
- [ ] Email provider: Resend or Nodemailer
- [ ] Image storage: Cloudinary or S3 (the signing code differs)
- [ ] Hosting for the API and a managed Postgres
- [ ] Express 4 or 5
- [ ] How to tell a project hidden by an admin from one hidden by its provider, so a provider cannot republish it (an extra field or a separate status)
- [ ] How to count profile views for provider analytics (a counter column or an event table), since the schema has none yet
- [ ] What a provider must complete before they can publish, and whether unverified providers may be published
- [ ] Budget range values, and whether project types and styles are lookup tables or enums
